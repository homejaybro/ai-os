# 既有專案改由 ai-os 管理

目標：專案改由外掛管理；專案專屬的規定、角色、紀錄不漏；不留兩套衝突的規則；程式碼與產出不變。先讀 `${CLAUDE_PLUGIN_ROOT}/rules.md`（轉換後要遵守的共用規則）。

git 指令一律 `rtk proxy git -c core.quotepath=false ...`（RTK 會改寫 diff 輸出；中文檔名才會正常）。下文 `<主線>` ＝使用者實際在用的分支，通常是 main 或 master；工作都在別的分支時，先問要不要把它當主線。

## 1. 判斷類型與能不能轉

- **A 舊 AI OS 範本**：有 `_開發檔案/scripts/hooks/verify-gate.ps1`（不論有沒有進版本）。
- **B 有自己的規則書**：有 `CLAUDE.md`、`AGENTS.md`、`.claude/agents/` 或 `.claude/skills/`，但不是 A。
- **C 沒有架構**：只有程式碼與文件。

任一項成立就停下，用白話說明並給建議：
- 已有 `_管理/常駐/此次任務.md` 而且不是 A → 已是 ai-os 專案。
- 不是開發專案（私人資料、單純文件夾），或從沒開工（沒有程式碼也沒有規格）→ 不轉；沒開工的建議用 `ai-os:start-project` 重開。
- （有 git 時）`git status --porcelain --untracked-files=no` 不是空的 → 請使用者先照專案原本的流程收尾、存檔。未進版本的檔（`??`）列出來即可，不擋。
- （有 git 時）`git worktree list` 有多個工作資料夾 → 只在 `<主線>` 所在的那份轉；其他分支先看 `git log <主線>..<分支>`，專屬內容第 3 步一起搬，轉完再問要不要收掉。
- 目前不在 `<主線>`，或有 merge／rebase 進行中 → 白話說明這個分支在做什麼，建議先回 `<主線>`。

`_管理/任務分解.md` 還有沒做完的切片 → 說明可以轉（內容不動），但建議在兩片之間做，讓使用者選。

## 2. 安全網與基準

- 沒有 git → 先把整個資料夾複製一份到旁邊當備份（依賴目錄 `node_modules`、`.venv` 不複製），再 `git init -b main`；`.gitignore` 先排除機密與依賴目錄；超過 50MB 的檔列給使用者看（GitHub 上限 100MB）；以現況做第一次 commit。
- `git tag backup-YYYYMMDD-HHMM`、`git checkout -b adopt-ai-os`。
- 跑一次建置、型別檢查、單元測試，記下結果當基準。需要登入或真實資料庫的測試不跑。沒有任何測試或建置指令 → 基準改用「主要畫面或指令能正常啟動」。

## 3. 盤點並決定去處（動手改檔前完成）

盤點範圍：專案內所有 Claude 設定與管理文件，加上使用者端此專案的自動記憶 `~/.claude/projects/<路徑編碼>/memory/`（每次對話都會載入，只讀不搬）。逐條歸類：

| 內容 | 去處 |
|---|---|
| 每次對話都要遵守的專案規定 | 新 `CLAUDE.md` 下方 |
| 技術棧、開發指令、資料夾規則 | `_管理/常駐/專案規格.md` 的 STACK_RULES |
| 已做的決定、踩過的坑 | `方案紀錄.md`；踩坑另成一檔的，保留原檔並在「三、踩坑」寫一句指向它 |
| 進度、待辦、階段 | `此次任務.md`：照範本段落結構，舊內容逐欄搬；舊的已完成表、允許改動清單移到檔尾「歷史紀錄」區，不刪 |
| 專屬角色、專屬技能 | 保留在專案 `.claude/` |
| 外掛已提供的（通用角色、通用流程、舊把關、舊規則書的共用部分）| 第 6 步移除 |
| 自動記憶裡跟共用規則衝突、或指向舊檔名的 | 列入第 4 步 |

- A：使用者若還保留舊範本倉庫（問一次位置），每個範本檔跟它的歷史版本比對，取差異最少的；比對加 `--ignore-cr-at-eol`。差異就是專案自己加的。倉庫不在、或找不到同名檔（例如 `00_` 開頭的舊命名）→ 同 B。
- B：逐段讀，判斷是專案專屬還是通用做法；判斷不了的列入第 4 步。
- C：從程式碼與文件推得上述內容。
- 原規定在新結構下會失效（寫死舊檔名、要求派已不存在的角色）→ 改寫成新結構的說法。

## 4. 一次問完

合成一次提問，每項附建議，使用者回「好」即照建議：
- 跟共用規則衝突的專案規定或自動記憶（常見：「push 到 main 會自動上線」卻規定一般 push 放行——共用規則把這種 push 算紅線）。
- 第 3 步判斷不了的內容。
- 專案的驗證指令不在存檔把關認得的清單（`${CLAUDE_PLUGIN_ROOT}/scripts/verify-gate.ps1` 的 `$verifyPattern`）→ 建議在 `package.json` 加 `"test"` 等它認得的指令，否則以後每次存檔都會被擋。
- 階段與目前進度（C 類沒有紀錄時）。

## 5. 加上新架構

- 舊常駐檔能一對一對應新檔的（例如 `00_此次任務.md` → `常駐/此次任務.md`），先 `git mv` 成新路徑保留歷史；內容併入別檔的，併完 `git rm`（踩坑檔除外）。
- 從 `${CLAUDE_PLUGIN_ROOT}/templates/project/` 只補 `_管理/`、`_產出/` 裡缺的檔（`cp -rn`，不覆蓋；`開案確認.md` 是新案用的，不補）。`.github/`、`playwright.config.ts`、`_開發檔案/tests/e2e/`、`.mcp.json` 只在專案是同類技術棧、而且自己沒有時才加。
- `CLAUDE.md`：改成範本格式，下方放第 3 步留下的專案規定；有 `AGENTS.md` 且沒被載入 → 加一行 `@AGENTS.md`。
- `.claude/settings.json`：保留專案的權限，補範本的；移除指向第 6 步會刪掉的腳本的 hook 與權限。
- `.gitignore`：只追加範本有、專案沒有的排除項。
- 照第 3、4 步填好常駐檔；`此次任務.md` 的「當前步驟」填目前進度（空的會被當成還沒開案）。
- 專屬角色加 `omitClaudeMd: true` 並補上紅線段落（照 `${CLAUDE_PLUGIN_ROOT}/agents/builder.md`）——它看不到共用規則，原檔看似有紅線也要補齊。

## 6. 移除被外掛取代的舊東西（A、B）

`git rm` 第 3 步標為移除的。`_開發檔案/scripts/hooks/` 連未進版本的檔一起從磁碟刪掉，否則外掛會一直把專案當舊範本、不載入規則。本次對話裡舊 hook 報錯屬正常，重開後消失，不要去修。

## 7. 驗證並存檔

1. 用第 5、6 步的改名與刪除清單逐一搜尋專案與自動記憶，引用除了歷史紀錄外 0 殘留。
2. 在 Bash 跑 `CLAUDE_PROJECT_DIR="$PWD" powershell -NoProfile -ExecutionPolicy Bypass -File "${CLAUDE_PLUGIN_ROOT}/scripts/load-rules.ps1"`：有輸出且含「紅線」。
3. 建置與測試結果與第 2 步基準一致。
4. 存檔：只動文件與設定時存檔把關會放行。動到程式碼類的檔（A 類刪掉的 `.ps1`、新加的 `playwright.config.ts`）會被擋 → 驗證指令與 commit 寫在同一行（例：`npm run build && git commit -m "改由 ai-os 外掛管理"`）。沒有這類檔卻被擋 ＝ 誤動了程式碼，回頭查。

## 8. 審查（專案自訂內容多才做）

有專屬角色、改過的把關、或多條專案規定 → `rtk proxy git -c core.quotepath=false diff <備份標籤>..HEAD > _管理/全分支diff.txt`，連同盤點表交給 `ai-os:reviewer`，專找：專屬內容漏搬、規則衝突、斷掉的引用、程式碼被改動。修完回第 7 步。

## 9. 給使用者看

白話報告：保留了什麼、移除了什麼、衝突怎麼定、驗證結果。使用者說「好」才 `git checkout <主線> && git merge --no-ff adopt-ai-os && git branch -d adopt-ai-os`，刪掉 `_管理/全分支diff.txt`。自動記憶要改的，照第 4 步的回答改。**推送另外問**；推送會讓網站上線時要講明。最後請他重開這個專案的對話，問「紅線第 5 項是什麼？」確認規則已載入。

中途放棄：`git checkout <主線> && git branch -D adopt-ai-os`，備份標籤保留。
