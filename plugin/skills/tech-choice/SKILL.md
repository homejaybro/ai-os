# 技術選型呈現

> 觸發時機：技術決策偏離推薦棧、或使用者有疑慮時，依此格式呈現。**是否觸發、要不要問使用者**的規則見 共用規則「先決策、後一路執行」與「紅線」。
> **評估清單、適用門檻、「架構決策」定義與呈現格式，全部以本檔為唯一來源**（共用規則只指過來、不重述）。

## 預設路徑（多數綠地小專案）

> **推薦棧**＝Claude 依專案類型給的主流預設組合（如 Web 應用用 Next.js + Supabase）。有疑慮就當作「偏離」處理。

開案採用推薦棧 → 免逐項評估，`_管理/開案確認.md` 記一句「採用推薦棧 X，未逐項評估」即可。
只有**偏離推薦棧**、或**使用者對某項有疑慮**時，才跑下方呈現格式。

## AI 內部評估清單（十六維度，給 AI 自己對照，不整份丟給使用者）

選型時 AI 在心裡過一遍，挑出兩個選項**真正有差**的幾項講給使用者聽；沒差的不用提。

| 類別 | 維度 |
|---|---|
| 現在的成本 | 開發成本／費用、上市速度 |
| 規模與體驗 | 同時使用人數／資料量、呈現效果／使用者體驗、速度／效能 |
| 長期維運 | 維護與接手難度、穩定性／成熟度、升級與淘汰風險、與現有技能的契合度、供應商／社群趨勢 |
| 風險與退場成本 | 綁定風險（Lock-in）、安全性與法規、與其他必要服務的相容性、授權條款風險 |
| 產品／市場特性 | 在地化支援、未來功能擴充彈性 |

> 清單本身不因專案性質增減；明顯不適用的在腦中略過即可。可複用的 base／kit 專案，「綁定風險」「授權條款風險」影響會被下游放大，不要略過。

## 適用範圍

僅限技術棧／框架／核心第三方服務層級、且不易逆轉（換掉需改動多處呼叫端，或需要資料遷移）的選型。單一函式的內部寫法、元件內部命名、不影響上述任何一項的重構不算。
例：換資料庫、導入 Redis ＝算；表單欄位加 debounce、函式拆兩個 ＝不算。

## 「架構決策」的定義、門檻與範例

**定義**：會影響系統整體結構、且事後要改代價很高（牽動大量既有程式碼）的技術性決定。

要不要拆微服務／單體、要不要換掉核心資料庫、要不要重新設計權限模型架構＝算；單一 API route 內部要不要拆函式、換個不影響上述任何一項的內部工具函式庫＝不算。

## 呈現格式（給使用者看，白話）

每個選項用一兩句話講「選它的好處／代價」，只講兩邊真正有差的 3–5 件事，用日常用語（花多少錢、多快做出來、以後好不好換掉），不用術語。最後給一個推薦，理由要對應前面講的差異，不可用「比較靈活」這種對不上具體差異的說法。

```
選項 A：{名稱}
  好處：…　代價：…
選項 B：{名稱}
  好處：…　代價：…
我推薦：{A 或 B}——因為 {對應上面某個差異}。
```

## 路線選擇輔助

- 要選路線且有多個做法：已有可運作版本 → 附截圖或短操作說明；還沒有 → 用輕量靜態草圖（HTML/CSS 示意）呈現差異，差異夠大才各做一份雛型。
- 換技術棧／服務時，上面的白話比較仍必填，草圖只是附加。
