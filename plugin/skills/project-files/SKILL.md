# 常駐檔與資料夾

## 一、資料夾規範

檔名用中文、不加數字前綴或流水號（`.claude/agents/` 的英文檔名例外）。

| 位置 | 放什麼 | 何時讀 |
|---|---|---|
| `_管理/常駐/` | 此次任務（含專案階段）、專案規格（含 STACK_RULES）、方案紀錄（決策與踩坑）、領域詞彙 | 見共用規則「啟動」|
| `_管理/` 根層 | 一次性實例：`開案確認.md`、`任務分解.md` | 開案／大型任務 |
| `_管理/specs/` | 每個功能一份 `{功能名}.md` | 開發該功能時 |
| `_產出/` | 非程式碼成品（`{主題}/`）與驗收截圖（`截圖/{功能名}/`）| 使用者要找成品時 |
| `_開發檔案/` | `tests/e2e/`（Playwright 測試腳本）| — |

共用的規則、技能、子 Agent、commit 閘門與格式範本都在外掛（`${CLAUDE_PLUGIN_ROOT}`），不放進專案。`${CLAUDE_PLUGIN_ROOT}/templates/forms/` 的範本永遠不直接填。

根層只有：`CLAUDE.md`（本專案專屬的補充）、`.gitignore`、`.mcp.json`、`playwright.config.ts`，以及 `.claude/`、`.github/`。程式碼依 STACK_RULES 放置；不在這張表裡的資料夾不要自己新增。改檔名或搬資料夾要全庫搜尋舊路徑一起改（原則三）。

## 二、常駐檔寫入規則

1. 先讀再寫，比照既有格式續寫；檔案不存在才依範本建立並告知。
2. `方案紀錄.md` 的脈絡區只追加、不改舊條目（速查表的「狀態」欄是唯一可以就地改的）；`此次任務.md` 的進度欄可以就地更新。
3. 領域詞彙：同一個業務概念需要解釋兩次以上 → 收斂成一個詞補進 `領域詞彙.md`（用使用者說得出口的詞；只放業務概念，技術規則留在 STACK_RULES）。
4. 踩坑：踩到「下次還會再踩、而且從程式碼或文件讀不出來」的坑 → 當次寫進 `方案紀錄.md`「三、踩坑」（標題＋根因＋修法）。
5. 決策記錄：技術選型、資料庫結構、UI 規範、部署、架構決策定案時（含預先核准的紅線事項）→ `方案紀錄.md` 速查表加一列（結論）＋脈絡區追加一則（原因）。
6. 階段完成：`此次任務.md` 的「專案階段」打勾，並打里程碑標籤（見共用規則「版本與備份」）。增減階段要記進 `方案紀錄.md`。
7. CoreBrain：里程碑或結案時，把有跨專案價值的踩坑整理進全域設定指定的 CoreBrain，再逐條勾掉 `方案紀錄.md` 的「待同步至 CoreBrain」區。

## 三、改已定案的決策

只是「這一步做得不滿意要重來」→ `git reset`（保留檔案修改）後重做，不用走這節。

| 類型 | 何時 | 做什麼 |
|---|---|---|
| 改某個已定案決策 | 例如換一個套件、改資料表設計 | 確認改哪條 → CodeGraph 查影響 → 技術選型或架構的變更，以及超出預先核准範圍的紅線事項，先問使用者；其他自己決定 → `方案紀錄.md` 速查表該列「狀態」改成「已被 #N 取代」、加新列 → 影響範圍大就照 `ai-os:big-task` 做 |
| 整個方案推翻 | 方向全錯 | 重新討論 → 重寫 `專案規格.md` → `方案紀錄.md` 速查表受影響的列全標「已被 #N 取代」（#N＝新方案的決策列）→ 舊程式碼照 `ai-os:big-task` 第二節退回 |

兩類都把變更原因追加到 `方案紀錄.md` 脈絡區。
