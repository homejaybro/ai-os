# 設計對話

產出：每個功能一份規格，加一頁讓使用者說一次「好」的決策總表。已在核准清單內的功能不走這個流程。

## 提問預算

1. 開案最多 7 題；之後每個階段最多 5 題。用完就不再問，剩下的缺口選推薦做法，寫進決策總表「我替你決定的事」。使用者說「你全部決定」→ 不問，直接出總表。
2. 只問：做什麼、給誰用、這次不做什麼；風格、用語、品牌感；花錢、申請外部帳號、真實世界資訊（GitHub 倉庫網址、要不要收款）。
3. 其餘自己決定：技術選擇（採推薦棧）、失敗與備援、邊界情況、誤用、半途中斷、空狀態、未來擴充、命名、檔案放哪、怎麼測。事實性的東西先用工具查（讀檔、CodeGraph、網路）。
4. 一次一題、白話、附建議答案，使用者回「好」即可。
5. 紅線預先核准（登入做法、資料存取規則、資料表）不另外問：你提建議，放進決策總表「需要你點頭的事」讓使用者一次點頭。

## 流程

1. 理解脈絡：讀 `_管理/常駐/專案規格.md`（STACK_RULES）、`方案紀錄.md`、`領域詞彙.md`（對話中用這裡的詞）、相關的 `_管理/specs/`。
2. 提問（遵守預算），並自己把盲點全部掃出來、逐項寫出預設處理方式。掃完分兩版：
   - 第一版就做（完整可用）：主要流程與反向流程（新增／讀取／修改／刪除、取消、返回上一步、撤銷）、空資料、重複送出、誤用與錯誤輸入、半途離開再回來、畫面美觀好用、使用者會用到的設定彈性；以及任何會弄丟資料、有安全風險、跟錢有關的情況。
   - 第二版再加（極端情況）：斷網或服務暫時掛掉、超長內容（例如一次貼上上萬字）、極大量資料、多人同時改同一筆、少見的裝置或瀏覽器等。寫進規格的「之後再加」，第一版不做。
   - 分不清時：一般使用者第一週會碰到 → 第一版；很少 → 第二版。
3. 技術選擇：偏離推薦棧或使用者有疑慮才呈現選項（`ai-os:tech-choice`），其餘自己選，記入 `方案紀錄.md`。
4. 每個功能寫一份規格 `_管理/specs/{功能名}.md`，格式照 `${CLAUDE_PLUGIN_ROOT}/templates/forms/功能規格範本.md`。驗收條件只列第一版要過的。有新增／修改／刪除的功能，從 `ai-os:crud-tests` 挑適用的項目寫進驗收條件（例如重複送出、F5 重送、刪除前確認、空資料、權限），不適用的略過；屬第二版的（斷網、多人同時改等）放「之後再加」。核准前就備好。
5. 送審（視情況）：這個階段有 3 個以上功能，或涉及紅線 → 派一次 `ai-os:reviewer`（模式二：設計文件審查），一次審完全部規格。發現的問題你自己補進規格；只有會改變產品意圖的才問使用者（算進提問預算）。
6. 決策總表：照 `${CLAUDE_PLUGIN_ROOT}/templates/forms/決策總表範本.md` 呈現（一個階段的多個功能合成一張）。使用者說「好」→ 把核准內容記入 `此次任務.md` 的核准欄與 `方案紀錄.md`，之後一路做到完成（開案時例外：先照 `_管理/開案確認.md` 的初始化步驟做完、請使用者重開，才開始寫功能）。使用者有不同意見 → 修正後再呈現。

## 注意

- 決策在主對話做，不交給子 Agent。
- 需要解釋兩次以上的概念 → 收斂成一個詞補進 `領域詞彙.md`。
- 判定是大型任務（定義見 `ai-os:big-task`）→ 接著照該技能拆成垂直切片。
